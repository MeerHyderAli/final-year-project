# Dataset and model

## Headline result — read this first

| Evaluation | Accuracy | Macro-F1 |
|---|---|---|
| In-domain (held-out **rendered** images) | **0.969** | 0.967 |
| Cross-domain (31 **real** product photographs) | **0.258** | — |
| **Domain gap** | **0.711** | |

The model is not merely worse on real photographs — it is **confidently wrong**.

- **48% of its wrong answers** carried a confidence of 0.80 or higher.
- **Mean confidence on wrong answers: 0.782.**
- It labelled a real spark plug *"Air Filter"* at **0.99** confidence.

This is the most important result in the project. It does not invalidate the design —
it **proves** the design. A system that asserted fitment from image similarity would
send a user to a shop with the wrong part, with the model's full confidence behind it.

## The two datasets

### 1. Procedural renders (`--synthetic`) — what the checkpoint trains on

480 images (60 per class) generated by `app/download_images.py:make_synthetic`.
Each class is drawn with the physical proportions of its real part family:

| Class | Rendered as | Discriminating features |
|---|---|---|
| oil filter | vertical canister, ~1.3:1, coloured paint, metal top rim | elongation, hue, brightness |
| fuel filter | narrower and taller, dark body, contrast band | elongation, low brightness |
| hydraulic filter | large pale canister — the biggest object in frame | area ratio, high brightness |
| air filter | bright pleated panel, tight vertical lines | edge density, brightness, extent |
| brake pad | two flat dark slabs + bright backing plate | low area, very low brightness |
| drive belt | long thin near-black strip | elongation > 6 |
| spark plug | small narrow tall, ceramic + threaded metal | small area, high elongation, high brightness |
| clutch plate | large grey disc with central hole | high hole ratio, circular Hu moments |

Degradations are applied so the model cannot key on a constant: Gaussian blur
0.4–1.3, brightness drift ±14, varied backdrop. Every file gets a perceptual hash.

**Why synthetic at all?** It makes the pipeline reproducible offline, on an exam
laptop, with no network and no licence questions. It is a *smoke test*, not a dataset.

### 2. Real photographs — what you must collect

The committed cross-domain evaluation used 31 real product photographs. **They are not
committed**: they are third-party copyrighted works and are git-ignored. The metrics
they produced are committed in `ai-service/reports/cross-domain.json`.

Collecting them also produced a finding worth reporting. Of 38 harvested images, **7
had to be discarded by hand as label noise** — four "brake pads" were *bicycle* brake
pads, one "spark plug" was a spark-plug *socket tool*, one was an assorted filter
display, one an adaptor kit. The exclusions and reasons are recorded in
`ai-service/eval/real-photos/EXCLUDED.json`.

> **Point for the report:** an unlabelled image harvest silently pollutes both training
> and evaluation. Curate, and record what you rejected and why.

## Splitting without leakage — and the bug that taught us why

Near-duplicate images landing on both sides of a split is the classic way to report a
97% accuracy that means nothing. `train.py:make_splits` therefore clusters images by
perceptual hash **first**, then deals whole clusters into train/val/test
**stratified within each class**.

The first implementation split by group globally. It put **four entire classes** into
train and **two others** into test. Validation macro-F1 was pinned at 0.000, early
stopping selected the epoch-1 weights without complaint, and the run finished looking
successful. Two lessons:

1. Always print the per-class composition of every split (the code now does).
2. An early-stopping criterion with no floor is a silent failure mode — if validation
   never beats chance the trainer now says so loudly instead of shipping the worst epoch.

## Features: 22 hand-crafted dimensions

`app/features.py`. At a few hundred images per class a frozen CNN memorises; a small
model over physical features generalises.

| Block | Dims | Contents |
|---|---|---|
| shape | 8 | log-aspect, elongation, extent, solidity, hole ratio, area ratio, Hu #1, Hu #2 |
| colour | 6 | mean RGB, saturation, warmth (R−B), value |
| hue | 4 | circular hue moments (saturation-weighted), colourful fraction |
| texture | 4 | edge density (strict/loose), gradient magnitude, local roughness |

A belt really is a long thin strip; a clutch plate really is a disc with a hole; an
air filter really is a bright textured panel. These features make the task learnable on
a small dataset. Sanity check: elongation measures 2.0 for a cylinder, 9.9 for a strip,
1.0 for a disc.

**Two bugs, both worth reading about.**

**1. Constant feature ÷ epsilon = noise amplifier.** `hole_ratio` is constant across
the dataset, so its std is 0. Standardising divides by std; clamping that to `1e-6`
made the augmentation noise (0.02) blow up to **±20 000**. Training sat at chance
accuracy with the loss frozen at 2.14 — looking, superficially, like a data problem.
A six-way bisect isolated it: every configuration except *raw-std + augmentation*
reached 1.000 train accuracy. Fix: floor the std (`features.py:STD_FLOOR = 0.05`).
*Never standardise with a raw std, and never clamp a divisor to a near-zero epsilon.*

**2. Log-compression can destroy signal.** Aggressive `log1p` scaling on Hu moments
pushed every shape into the range 5.1–7.3 — finite, well-behaved, and practically
constant. Metrics looked healthy; the features carried almost no information. Diagnosis
came from a per-block F-ratio (between-class vs within-class variance) and a
nearest-centroid probe. Both are cheap and should be run before any training.

## Model

`app/model.py` — MLP, 22 → 128 → 64 → 8, BatchNorm, dropout 0.35, ~6k parameters.
Deliberately small: a bigger head over a small dataset just fits the noise.

- Class weights (√-balanced) and label smoothing 0.08.
- AdamW, lr 2e-3, cosine schedule, early stopping (patience 15), seed 42.
- **Temperature calibration** on the validation split, so "82% confident" means roughly
  82% correct. Fitted temperature is 0.5 (the grid's lower bound — the model is
  *under*-confident in-domain, which is the safe direction to err).

## Domain-shift detection — a negative result

Given that softmax confidence is untrustworthy out-of-domain, can we flag shifted
inputs cheaply? Measured on the real-photo set:

| Detector | Real photos flagged as OOD |
|---|---|
| Diagonal (per-feature z-score) distance | **0%** |
| Full Mahalanobis distance | **35%** |

Real product photos sit as close to the training *mean* as the renders do — they are
drawn from a different region of **label** space, not a distant region of **feature**
space. `app/ood.py` therefore ships as an **advisory** whose own payload states its
~35% detection rate and warns that a low distance is *not* a clean bill of health.

> **Point for the report:** you cannot buy your way out of a domain gap with a novelty
> detector. You fix it with real labelled data.

## What actually protects the user

Since neither confidence nor OOD distance is sufficient out-of-domain, the safety
comes from the product design:

1. The vision model outputs a **category**. It never sees fitment data.
2. `MIN_CONFIDENCE = 0.55`; below it the API answers `ask_for_more_info`.
3. Fitment is asserted **only** from a part-number match or a vehicle-catalogue match.
4. Safety-critical categories (brake pads, clutch plates) require a part number even
   when the catalogue lists a fitment — verdict `needs_part_number`.
5. Every response carries the domain-gap advisory, and the UI displays it.

## How to close the gap (future work)

1. **Collect 150–300 real photographs per class**, same phone, varied angle, lighting,
   dirt and wear. This is the single highest-value task.
2. Re-run the leakage-safe split and retrain; expect the in-domain number to *fall*
   and the real-world number to rise — that is the correct trade.
3. Only once ≥300 images per class exist, swap the hand-crafted features for a frozen
   CNN backbone (`train/train.py --backbone mobilenet`), fine-tuning the last block.
4. Re-evaluate with `train/evaluate.py --external-dir …` against photos held out
   entirely from training. Report both numbers, always.

## Reproduce everything

```bash
cd ai-service
python -m app.download_images --synthetic --per-class 60 --out ../data/images
python train/train.py --data data/images --epochs 80 --seed 42
python train/evaluate.py --model models/part_classifier.pt --data data/images \
       --external-dir ai-service/eval/real-photos --out reports/cross-domain.json
```

Outputs: `models/part_classifier.pt` (+ `.json` with full metrics and the OOD
parameters), `reports/metrics.json`, `reports/training-history.json`,
`reports/cross-domain.json`.
